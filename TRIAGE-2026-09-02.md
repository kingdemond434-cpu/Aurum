## The headline is wrong

**"Aurum is unprofitable" is not yet a measurement.** The number behind it is
`edge: -0.125R per trade over 37 resolved (15 wins)`. Three reasons it cannot carry that claim:

- **n = 37.** At a typical R-distribution, the standard error on mean R over 37 trades is roughly
  ±0.16R. −0.125R sits comfortably inside noise. The desk's own gate requires **30 resolved trades
  before a deflated Sharpe is even computed**, and 37 barely clears its own floor.
- **`ledger integrity: 26 duplicate decision_id(s)`.** Some fraction of those 37 may be the same
  decision counted twice. Until the duplicates are resolved, the denominator is unknown.
- **`spread profile: absent — every expectancy figure is priced against the FEED's spread, not the
  venue that actually fills you`.** And the venue check is failing because the attached terminal is
  **Fusion Markets, not Vantage**. So the cost model is measured against the wrong broker.

−0.125R over 37 trades with duplicate rows and the wrong spread model is not a verdict on the
strategy. It is a reading taken with a broken instrument. **Do not rebuild the architecture on it.**

## What is actually broken

### 1. The learning loop has been dead for 15 days

```
AurumSignalDesk-Cycle :: last run exited 1 — the whole learning loop is firing and FAILING
  PermissionError: [Errno 13] Permission denied: 'C:\Aurum\state\cycle.log'
```

`state/cycle_state.json` still reads `last_run: 2026-08-18`. Every recorded cycle run was also a
dry run (`nothing sent, day NOT stamped`). So **nothing has been learned since 18 August**,
independent of anything else in this document.

Cause: `log()` in `aurum_cycle.py` opened the log file and let the exception propagate. It is
called before any real work, so the cycle died before writing line one — which is why there is no
`update.log` to read. Windows does not share an open file the way POSIX does, so any concurrent
holder (a second cycle, the watchdog, a tail, antivirus) makes the append fail.

**Fixed in this commit.** The log is a record of the run, not the run: it now prints and continues.

## The one real finding

```
selection :: taken trades resolve -0.13R while refusals reached +1.20R at best.
             The analyst is selecting AGAINST itself — that is not caution, it is
             being wrong in a direction no win-rate shows.
```

This is the only result in the whole state file that is about *gold decisions* rather than
plumbing, and it is the one worth working on. The desk is not failing to find setups. It is
finding them, then systematically taking the worse half.

**More context cannot fix this.** A selector that is anti-correlated with outcome does not become
correlated when given more to look at — it becomes more confidently wrong, more slowly, at higher
token cost. If the ranking is inverted, additional inputs sharpen the inversion.

The cheap diagnostic: take the refusal ledger (`REFUSAL_COMPILER` 93, `REFUSAL_MODEL` 114) and
resolve every refusal forward as if it had been taken. If refusals systematically outperform takes
across the sample, the selection boundary is pointed the wrong way and that is a one-line change to
test, not an architecture programme.

## On "24/7, all timeframes, all context"

The instinct behind it is right — there is a real coverage problem, and 1,030 blind bars is it. But
the fix for blind bars is **making the analyst answer**, not giving it more to look at. Right now:

| Adding more context would… | Current state |
|---|---|
| multiply per-decision token cost | analyst already fails 100% of wakes |
| raise latency per decision | 1,030 bars already unanswered |
| add trials to the search | 3,168 trials already un-haircut |
| require the learning loop to evaluate it | loop dead 15 days |
| be priced against a cost model | spread profile absent, wrong broker |

Every one of those is a multiplier on a broken denominator. The breadth is not the constraint; the
desk cannot currently measure whether *any* input helps. Context expansion is the right project
**after** the loop runs, the analyst answers, and the ledger is clean — at which point the negative
control panel in `canonical/2026-08-13-negative-control-markets.md` can tell you which added
context is gold-specific signal and which is generic noise.

it simply is not established yet. The correct posture is that **the desk's profitability is
currently unmeasured**, not negative — and that the cheapest path to knowing is repair, not
expansion.
